# 3D뷰(신규 테스트) — 구성·시도·실패·다음 방향 총정리

> 대용량 통합모델(평택-오송 5공구, **4.1억 삼각형/8.5GB**)을 **자체 엔진(xeokit 기반, ACC 비종속)**
> 으로 웹에서 ACC 수준으로 띄우는 것이 목표. 이 문서는 지금까지의 전 과정을 솔직히 정리하고
> 방향을 바로잡기 위한 기준 문서다.

---

## 0. 목표 (다시 확정)
- **자체 엔진.** ACC(오토데스크 APS 뷰어)에 **종속되지 않는다.** APS 뷰어 임베드는 선택지 아님.
- 웹 브라우저 + **약한 클라이언트**에서 대용량 BIM을 ACC처럼: **빠르게 열리고, 점진적으로 끝까지
  채워지고, 부드럽게 회전**.
- 원본 형상 유지(깍두기/덩어리 거부).

## 1. 모델 실측 (모든 판단의 근거)
| 항목 | 값 |
|---|---|
| 구조물 삼각형(flatten) | **412,096,117 (4.1억)** |
| 고유 삼각형(인스턴싱 후) | 179,953,547 (1.8억, 반복배수 2.29×) |
| 부재(객체) 수 | 490,143개 |
| 원본 총량 | ~8.5GB |
| 지형(항공사진 드레이프) | 1.15M 삼각형 · **243MB**(대부분 텍스처) — **잘 됨/빠름** |
| "큰 부재만" 개요(대각≥20m) | 3,800만 삼각형 · **~650MB** (전혀 안 가벼움) |
| "큰 부재만" 개요(대각≥8m) | 9,960만 삼각형 · ~1,700MB |

**핵심 사실:** 이 모델엔 **"가볍고 깨끗한 개요"가 존재하지 않는다.** 큰 부재조차 삼각형이 촘촘하다.

## 2. 클라이언트 예산 (실측 추정)
- 지형 1.15M 삼각형 · 243MB = **빠름/부드러움** → 이게 쾌적 기준선.
- 그 이상(수천만 삼각형 상주, 수백MB↑ 순간 로드)은 **느려지거나 멈춤**.
- 병목: **약한 GPU(정점 처리) + 제한된 대역폭 + 대용량 XKT 파싱(메인스레드 프리징)**.

## 3. 파이프라인 구성 (현재)
```
APS Model Derivative(SVF)  →  svf-utils 파싱  →  scripts/mergeGlb.mjs (GLB 청크)
   →  @xeokit/xeokit-convert(convert2xkt)  →  XKT  →  Cloudflare R2 (+manifest.json)
   →  api/aps-convert.ts (R2 presigned URL)  →  src/pages/ThreeDTest.tsx (xeokit XKTLoaderPlugin)
```
- 변환은 **GitHub Actions**(`.github/workflows/convert-4d.yml`, 1073타일 빌드 ~45분).
- 배포 Vercel. 지형은 **항상 로드 베이스**로 분리(243MB), 구조물은 **200m 공간 타일**(원본).
- 현재 캐시: **타일 1,073개 · 평균 7.9MB · 개요(lod1) 15MB · 최초 ~258MB**.

## 5. 실패에서 배운 확정 사실 (제약)
1. **깨끗하게 감량하는 도구가 없다.** meshopt `simplify`=shard, 격자클러스터=깍두기, `simplifySloppy`=이 빌드에 없음. → **모든 "가벼운 깨끗한 표현"의 근본 장벽.**
2. 원본은 **균일하게 촘촘**하다(큰 부재도 무거움). 객체 크기 필터로 가벼워지지 않음.
3. 스트리밍은 **깨끗하나 불완전**(넓은 뷰=데이터량·구멍). 개요는 **완전하나 거침**.
4. 인스턴싱은 지오메트리는 줄이나 **엔티티 수(21.8만)**가 약한 클라이언트를 초크.
5. 최초 로드는 지형(243MB) 수준까진 쾌적. 그 이상 항상로드는 부담.

## 6. ACC가 되는 이유 (우리에게 없는 것)
ACC(APS 뷰어)가 같은 모델을 잘 띄우는 핵심:
1. **SVF 네이티브 점진 스트리밍** — 조각을 점진 로드(“로드 중…”), 우리도 점진은 함.
2. **부재별 화면크기 기반 LOD(screen-space-error)** — **멀리/작게 보이는 부재는 자동 저디테일**로 그려, 뷰를 가득 채워도 무겁지 않음. ← **우리에게 없는 결정적 조각.**
3. **정교한 GPU 메모리 관리 + 오클루전 컬링** — 안 보이는 것/가린 것 안 그림.

우리는 지금 "**보이면 원본, 안 보이면 안 뜸**"의 이분법이라, 채우면 무겁고 안 채우면 구멍이다.
ACC는 그 사이 **연속적 LOD**가 있다.

## 7. 핵심 미해결 문제 (여기를 뚫어야 함)
> **부재별 다단계 LOD(화면 크기로 자동 선택).** 이게 있으면 완전+빠름+깨끗(=ACC 패리티).
> 그런데 이걸 만들려면 **깨끗한 감량기**가 필요 — 그게 5-①의 장벽.

**즉, 진짜 병목은 "쓸만한 지오메트리 감량기"다.** 이걸 확보하면 나머지(LOD 계층, 스트리밍)는 조립 가능.

## 8. 다음 방향 (우선순위)
**A. 감량기 문제부터 정면 돌파 (최우선, 자체 엔진의 관건)**
   - meshopt `simplify`를 **weld 후 + 중간 비율(50~25%) + 속성보존(simplifyWithAttributes)**로 재실험
     (과거 shard는 극단 비율에서였음 — 중간 비율은 미검증).
   - 대안 도구: **gltfpack**(meshopt LOD), **Draco**, 또는 **부재별**(전역 아님) 클러스터 감량
     (부재 단위면 경계붕괴 shard가 원천 축소).
   - 목표: 원본 형상 유지하며 **2~4단 LOD** 생성(예 100%/40%/12%).

**B. 감량기 확보되면 → 부재별 LOD 계층 + 화면크기 선택 (ACC식)**
   - 각 타일/부재에 LOD 레벨 부여, 뷰어가 화면상 크기로 레벨 선택 → 채워도 가벼움.

**C. 감량기 확보 전까지의 현실적 최선 (임시)**
   - 현재 "원본 타일 점진 완성"(look 기준·개수제한 해제) 유지 + GPU 메모리 상한.
   - 넓은 뷰 완전 커버는 물리적으로 포기(줌인 작업뷰 위주 최적화).

## 9. 지금 상태 요약 (한 줄)
