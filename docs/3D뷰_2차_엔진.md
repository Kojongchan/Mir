# 3D뷰 2차 엔진 — 표준 계층형 타일(3D Tiles) + three.js

> 결정 D23. 기존 xeokit 화면(`3D뷰 (신규 테스트)`)은 그대로 두고 `3D뷰 (신규 테스트 2차)` 에서 같은 모델로 비교한다.
> 목표: **현장 PC·태블릿·모바일에서도 죽지 않고 빨리 뜨고 부드럽게** — 기기마다 정해진 예산 안에서 화면에 필요한
> 만큼만 그린다.

## 1. 왜 바꾸나 (요약)
- 지금(xeokit)은 타일마다 원경/경량/상세 3단을 **우리가 직접** 고르고, 원경은 현장 전체(1,073개·≈1,600만 삼각형)를 항상
  상주시킨다. 데스크톱은 되지만 모바일·저사양엔 무겁고, 화면 크기에 따른 연속 LOD 가 없다(`3D뷰_구성정리_및_방향.md` 6·7절).
- 업계 표준(OGC **3D Tiles**)은 공간 계층(HLOD)과 **화면 오차(px) 기반 선택**, 메모리 상한·LRU 해제가 규격·렌더러에 들어 있다.
  대규모 토목·도시 모델(수 km 선형 현장)이 정확히 이 형식의 주력 영역.
- 라이선스: xeokit = AGPL-3.0(상용 시 소스 공개 또는 상용 라이선스). three.js(MIT)·3DTilesRendererJS(Apache-2.0)·
  meshoptimizer(MIT)·camera-controls(MIT)는 상업 사용 자유.
- 예전 three.js 시도(6~7월)는 **브라우저가 IFC 를 그 자리에서 해석**해 실패. 이번은 서버 사전변환 + 표준 HLOD 라 처음.

### 1차(xeokit) 대 2차 — 무엇이 다른가 (2026-10-13 사용자 질문 "왜 훨씬 가볍고 선택도 깔끔한가")
| | 1차 `3D뷰 (신규 테스트)` | 2차 `3D뷰 (신규 테스트 2차)` |
|---|---|---|
| 받는 방식 | 우리 코드가 거리·화면 위치로 타일별 원경/경량/상세를 고름. 현장 전체를 보려면 원경 1,073파일(1,680만 삼각형)을 다 받음 | 표준 3D Tiles: 현장 전체 1MB(15만 삼각형) 하나 → 화면에서 오차가 몇 px 넘는 곳만 더 세밀한 조각으로 교체(HLOD) |
| 파일 | XKT(xeokit 전용), 지형 사진은 패딩 포함 216MB | glTF + meshopt 압축 + int16 좌표(같은 형상 ≈1/5), 사진 KTX2 4.7MB |
| 객체 관리 | 25만 객체 × 단계별 엔티티를 CPU 가 각각 관리 | 타일당 그리기 1~2번, 정점마다 객체번호(dbId)만 심음 |
| 선택·강조·숨김 | 같은 면을 한 번 더 그림/객체별 색 변경 → 점박이·조각 문제 | 객체번호→상태 표(텍스처) 한 장을 셰이더가 읽음: 표 한 칸 바꾸면 모든 단계·타일에 즉시 |
| 클릭 | CPU 광선 판정 | GPU 1픽셀에서 객체번호·깊이 읽기 |
| 그리기 | 매 프레임 | 카메라·타일·상태가 바뀔 때만(정지 0fps) |
| 기기 | 공통 | 고성능/현장 PC/모바일 등급별 화면 오차·메모리 상한 |
| 라이선스 | AGPL-3.0 | MIT/Apache-2.0 |
근접에서 보이는 원본(상세)은 같은 데이터라 아주 가까이에선 비슷하게 무거움 → 중간 단계가 다음 과제.

멀리서 볼 때(화면 크기 기준이라 상위 단계): 상위 단계에서 사라진 긴 부재는 방향 맞춘 상자로 대신 남김(`proxyBoxes`), PC 는 MSAA.
보고서용 캡처는 「고화질 캡처」 — 화면을 2배 해상도로, 보이는 모든 부분을 1.5px 오차까지 불러온 뒤 PNG.

## 2. 데이터 (서버, `diag_only=tiles3d`, `scripts/build-tiles3d.mjs`)
```
R2 기존 타일(XKT: 원경 far v5 / 경량 light v2 / 상세 원본) + 조각 연결표(meta/alias)
  → 디코드(scripts/tile-lod-merge.mjs) → 메시별 월드 좌표·색·엔티티
  → glTF 2.0 (.glb): 타일당 primitive 1개(불투명) + 1개(반투명), int16 양자화(KHR_mesh_quantization)
     + EXT_meshopt_compression, 정점 속성 _FEATURE_ID_0 = dbId(조각 연결표로 entity-N 도 원래 객체로), 법선 없음(플랫 셰이딩)
  → 상위 단계: 원경 타일을 공간적으로 묶어 병합·추가 감량(meshopt, 절대오차 2·4·8·16…m + Prune) → 루트까지
  → tileset.json (REPLACE 세분화, boundingVolume box, geometricError = 각 단계 오차)
  → R2 <prefix>/tiles3d/runs/<id>/ + <prefix>/tiles3d/current.json
```
- 좌표: XKT 디코드 좌표(= SVF − 변환 원점, Z-up)를 그대로 tileset 좌표로. glTF 는 Y-up 규격이라 (x, z, −y) 로 넣고, 타일
  중심은 노드 translation(정밀도: 타일 중심 기준 양자화, 행렬은 JS 배정밀도 → 지터 없음).
- 범위(2026-10-13~): 원경 + 상위 단계 + **원본(상세) 모두 현장 전체**. 경량(light)은 원본 대비 삼각형이 26%밖에 안 줄어 생략
  (저장 ≈0.8GB 절약). 원경이 원본 삼각형의 90% 이상을 이미 가진 타일은 원본 사본을 만들지 않음. 원경→원본 전환 오차 3m(현장 PC 기준
  ≈200m, 1차 화면의 원경 전환 거리와 같음). `region=<타일>:<개수>` 옵션은 빠른 시험 빌드용(그 구간만 원본).
- **지형**: 1차 화면이 항상 로드하는 지형 베이스(`manifest.base`, b*.xkt, 1,274패치·115만 삼각형·항공사진 54장)를 사진마다 잎 타일
  1개(KTX2 그대로 임베드, KHR_texture_basisu)로, 상위는 같은 사진 + 단순화(2·6m, 사진 경계 고정 → 틈 없음). XKT 안 사진 슬롯은
  4MB 고정 패딩이라 216MB였지만 실제 KTX2 는 장당 ≈90KB(총 4.7MB). 뷰어는 지형만 조명 사진 재질(객체 ID 없음 → 선택 제외,
  클릭 시 회전 중심은 지형 표면), 「지형」 버튼으로 켜고 끔. tileset 루트(내용 없음) 아래 구조물·지형 두 갈래(`extras.mir`).
- 객체 박스 색인(`objects.bin`, dbId 마다 박스 6개 float32): 검색 결과 "확대"용.

## 3. 뷰어 (`src/pages/ThreeDTest2.tsx`, `src/viewer2/`)
- three.js `WebGLRenderer`(일반 깊이 버퍼 — reverse-Z 는 r171 + 소프트웨어 GL 에서 아무것도 안 그려 제외, 대신 근평면은 궤도 거리·원평면은 모델 경계에 맞춰 정밀도 확보), `TilesRenderer`(3d-tiles-renderer) + GLTF 확장 플러그인
  (meshopt 디코더, 워커) + 서명 URL 플러그인(상대경로 → R2 presigned).
- 단계 선택: `errorTarget`(px)·`lruCache.maxBytesSize`·해석 동시 수를 **기기 등급**(고성능/현장 PC/모바일)으로 설정. 화면 해상도
  배율 상한(모바일 1~1.5).
- 재질: 공유 `MeshLambertMaterial`(정점색·플랫 셰이딩) 1종 + **dbId 상태 텍스처**(RGBA8, 1024×N): 선택(파랑)·검색 강조(주황)·
  숨김(트리 체크)을 셰이더가 읽음 → 모든 단계·나중에 로드되는 타일까지 자동 적용, 추가 그리기 패스 없음(점박이 원천 차단).
- 클릭: GPU 픽(1×1 렌더 → dbId) + 깊이 픽(회전 중심). 조작: camera-controls(커서 쪽 줌, 누른 지점 기준 회전, 터치).
- 속성·트리·검색·값 검색: 기존 색인/패널 재사용.
- 성능 표시: fps, 드로콜, 그린 삼각형, 로드/표시 타일, 캐시 MB, JS 힙.

저사양(CPU 4배 감속)·모바일 뷰포트 조건. 자동 점검(`scripts/ui-check.mjs`)에 2차 화면 측정 추가.

### 객체가 늦게 뜨고 멀어지면 불안정 (2026-10-13, 사용자 스크린샷 3장)
**불안정 = 깊이 다툼.** 실제 타일 931 에서 녹색 사면 정점 921개가 회색 면과 5cm 이내(p10 5mm)로 겹쳐 있음(사면 마감과 토공 본체,
배수로 등). 근평면이 궤도 거리 × 0.002(최소 5cm)라 수백 m 밖에선 표준 깊이 버퍼가 이 층들을 가르지 못해 흰 톱니가 깜박임.
같은 원본을 300m·근평면 5cm 로 그리면 표준 버퍼는 톱니, **로그 깊이 버퍼는 깨끗** → PC 등급에 로그 깊이 버퍼(픽킹도 같은 깊이),
모바일은 표준 유지(픽셀마다 깊이 쓰기가 타일형 GPU 의 숨은 면 제거를 막음 — 모바일이 4px 로 고운 단계를 그리게 된 뒤 모든 등급 로그 깊이, 아래 「휴대폰·태블릿 기준」). 단순화 사본의 면적 손실은 931 에서 2~10% 로 원인 아님.

**늦게 뜸 = 요청 지연.** 배포 화면(고성능 PC)에서 환기구#16 확대: 타일 요청 215개·20MB 에 21.7초. R2 는 HTTP/1.1, 첫 바이트까지
0.35~0.85초, 브라우저는 호스트당 6연결 → 대역폭이 아니라 "요청 수 × 지연 ÷ 6" 이 시간을 정함. 조치:
- **두 호스트 이름**: API 가 타일 파일을 하나 걸러 버킷 자체 호스트(`<bucket>.<account>.r2…`)로 서명 → 동시 12개(배포에서 최대 25개 진행).
- **각 시점의 타일만 직접**(`loadAncestors=false`): 거친 단계를 먼저 받지 않고, 화면에 있던 것은 대체될 때까지 유지.
- **브라우저 타일 보관**(Cache Storage, 모델별·실행 run 과 경로 키): 서명 URL 이 매번 달라 HTTP 캐시가 안 먹던 것 → 재방문은 네트워크
  없이. 새 run 이면 그 모델 보관본을 비움. 상태줄 「저장본 N」.
- 다운로드 동시 수 현장 PC 8 → 12, 모바일 6 → 8.
